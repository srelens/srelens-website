Investigate OOMKilled before increasing the limit.

Confirm the kernel termination, reconstruct what the process was doing, and distinguish a legitimate capacity change from a leak or unbounded workload.

Memory pressure10-minute runbookMetrics Server optional
In this guide
  • Confirm OOMKilled
  • Reconstruct the failure
  • Compare limits
  • Review the change
  • Verify recovery

1. Confirm the termination

Open the pod detail and identify the affected container. Verify that the last termination reason is OOMKilled; exit code 137 is a supporting signal but should not replace the explicit container state.

Check restart count, QoS class, node placement, and whether sibling replicas failed at the same time.

2. Reconstruct the last instance

Open Logs, select the affected container, and enable prev and ts. Look for large batch operations, cache warm-up, concurrency spikes, expensive requests, or a steady increase before termination.

If Metrics Server is available, compare the pod or controller memory graph across 5m, 10m, 30m, and 1h ranges. Metrics may show the direction of travel even if the final peak was missed.

3. Compare observed demand with the manifest

Follow the owner link to the workload and open YAML. Review container memory requests and limits, replica count, environment flags that affect concurrency or caching, and any recently changed command arguments.

PatternPossible next investigation
Immediate failure after startupStartup heap, migration, cache load, or configuration expansion
Steady rise across timeLeak, retained queue, cache growth, or missing bounds
Multiple pods fail togetherTraffic spike, synchronized job, rollout change, or node pressure
Only one replica failsSkewed traffic, hot partition, pod-specific data, or node conditions

4. Review a controlled change

A higher limit may be correct, but it can also delay a repeat incident. Make the application or resource change through the workload’s normal deployment path when possible. If editing in srelens, use the YAML Changes view for a server dry-run diff before applying.

Check node capacity

Increasing a container limit without checking node allocatable memory and workload density can move the incident from a pod-level OOM to broader node pressure.

5. Verify recovery

Watch the rollout, desired replicas, pod readiness, restart count, events, and memory graph. Recovery means the workload remains healthy through the conditions that triggered the failure—not merely that the newest pod started.
