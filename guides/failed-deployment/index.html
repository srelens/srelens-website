Trace a failed deployment through its rollout graph.

Start with controller conditions, then follow the active revision to ReplicaSets and pods before choosing rollback, edit, or restart.

Deployment15-minute runbookRollback-aware
In this guide
  • Read rollout state
  • Follow relationships
  • Collect evidence
  • Review manifest
  • Choose recovery

1. Read the controller state

Open Workloads → Deployments and select the affected controller. Compare desired, updated, available, and unavailable replica counts. Read progressing and available conditions before interpreting the rollout as stuck or failed.

Check recent events for quota denials, scheduling failures, image pull errors, probe failures, or admission-policy rejection.

2. Follow the active revision

Use the workload relationships to open its ReplicaSets and pods. Identify whether the newest revision created pods, whether old replicas remain available, and whether failures are isolated to the new template.

ObservationLikely investigation path
No new podsAdmission, quota, selector, controller, or image configuration
Pods PendingScheduling events, resources, volumes, affinity, or taints
Pods crash loopingPrevious logs, container state, probes, command, configuration
Pods Running but unavailableReadiness probe, service dependency, or application initialization

3. Collect pod-level evidence

Open a failing pod. Read its Overview, Events, and container state. Stream workload logs to compare replicas; use prev for crashed instances. Open a shell or attach an ephemeral debug container only when it adds evidence unavailable through status, logs, and events.

4. Review the manifest and rollout history

Inspect image tags, commands, environment sources, volumes, probes, security context, and resource policy. Compare the change with the previous revision in your delivery system. srelens can show workload revisions and a dry-run YAML diff before a server-side apply.

5. Choose the smallest safe recovery

  • Rollback when the current revision is known-bad and the previous revision remains valid.
  • Fix forward when the correction is understood, reviewed, and safer than restoring the prior version.
  • Rollout restart when configuration or credentials changed outside the pod template and restarting is an intentional reload mechanism—not as a generic first response.
  • Scale only after considering capacity, dependencies, and how the change affects the incident.
Prefer the deployment pipeline

During an incident, direct edits can restore service but also create configuration drift. Record the exact mutation and reconcile it with source control immediately.

6. Confirm rollout health

Watch updated and available replicas converge, confirm readiness across the new pods, and monitor events and logs through the original failure window. Validate the user-facing or service-level symptom that started the investigation.
