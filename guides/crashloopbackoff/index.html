Debug CrashLoopBackOff from the last failure backward.

The restart loop is a symptom. Start with the previous container instance, then correlate its exit state with events, configuration, and dependencies.

Pod lifecycle10-minute runbookEvidence first
In this guide
  • Confirm the state
  • Read previous logs
  • Inspect events
  • Review configuration
  • Debug the container

1. Confirm which container is restarting

Open Workloads → Pods, filter by namespace or workload name, and select the affected pod. In Overview, identify the container with a non-zero restart count and read its last termination reason, exit code, readiness state, and condition timeline.

Do not start by deleting the pod

A replacement may enter the same loop and remove the most convenient path to previous-instance logs and local evidence.

2. Read the previous container instance

Open Logs for the failing container. Enable prev to request logs from the terminated instance, then enable ts to correlate the last output with Kubernetes events.

Look for configuration parsing failures, unavailable dependencies, permission errors, failed migrations, bind errors, or an explicit process exit. If the log buffer contains multiple sources, select the affected pod and container before drawing conclusions.

3. Inspect object and scheduling events

Open the pod’s Events tab. Image pull failures, mount failures, probe failures, admission denials, and scheduling problems may explain the restart without requiring application-level debugging. Follow owner links to the controller and compare sibling pods.

4. Review the workload manifest

Follow the pod’s controller link and open YAML. Check command and arguments, environment sources, volume mounts, probes, security context, and resource limits. If a fix is required, use Changes to run a dry-run diff before applying it with server-side apply.

5. Use the least invasive debugging path

  • If the image contains a shell and stays alive long enough, open the pod Shell.
  • For a minimal or distroless image, use Debug to attach an ephemeral container and optionally share the target container’s process namespace.
  • If the process exits before inspection, reproduce its environment in a controlled non-production workload rather than repeatedly mutating the failing pod.

6. Verify recovery

After the deployment pipeline or reviewed manifest change runs, watch pod readiness, restart counts, events, and live logs. Confirm the controller reaches its desired replicas and that the original error signal clears.
