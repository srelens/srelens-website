Desktop security model

BoundaryBehavior
Credentialssrelens reads the default kubeconfig and files listed in KUBECONFIG. Added files remain local; pasted configs are stored in the application directory.
Cluster trafficThe desktop application connects directly to Kubernetes API servers. There is no intermediary srelens cloud service in the desktop path.
AuthorizationAvailable operations are governed by the Kubernetes credentials and RBAC permissions of the selected context.
SecretsSecret values are masked by default and revealed per key. Changes still respect Kubernetes RBAC.
Application logsRotating local logs help diagnose failures and are distinct from Kubernetes workload logs.

Guarded mutations

Actions are preflighted against RBAC. Unsupported operations are disabled with a reason. Destructive actions such as delete, evict, node drain, context removal, plugin installation, and Helm uninstall require explicit confirmation.

Confirmation is not authorization

The confirmation gate reduces accidental execution. Kubernetes RBAC remains the authority that determines whether the operation can succeed.

MCP access

  • stdio clients launch srelens --mcp-stdio.
  • HTTP transport binds to 127.0.0.1 and is not exposed on external interfaces by the desktop app.
  • MCP tools use the same locally authenticated cluster contexts as the desktop interface.
  • Tools marked as mutating or destructive reject calls without an explicit "_confirm": true argument.

Operators should still review agent tool calls and restrict access to critical clusters with appropriate Kubernetes roles.

Updates and packages

macOS builds are Developer ID signed and notarized. Tauri updates are cryptographically signed and verified before installation. Windows code signing remains on the project roadmap, so Windows may display SmartScreen during installation. Linux assets include Tauri updater signatures; GPG signatures are planned.

Web deployment is a separate trust model

The optional multi-user web server does not inherit the desktop security model. Production deployments require authentication, TLS termination, a stable master key, and RAM-backed storage for decrypted runtime material.

  • Server mode refuses to start without a 32-byte SRELENS_MASTER_KEY.
  • Uploaded kubeconfigs and OIDC tokens are sealed at rest with AES-256-GCM and scoped to the authenticated user.
  • Decrypted per-user files should live on the documented tmpfs mount, not persistent storage.
  • The development login must never be enabled on a public deployment.
  • Desktop-only host-shell and process-wide toolbox operations are blocked in shared web mode.

Read the complete deployment requirements in the web-mode security guide.

Reporting a vulnerability

Use the repository’s Security page for current reporting instructions. Avoid publishing credentials, kubeconfigs, cluster endpoints, or sensitive application logs in a public issue.
